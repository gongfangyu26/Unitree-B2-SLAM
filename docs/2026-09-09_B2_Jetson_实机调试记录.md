## 4. B2 安全短运动测试

测试程序：

``` text

```

测试参数基础值：

-   前后速度：0.30 m/s
-   横向初始速度：0.08 m/s
-   角速度：0.20 rad/s
-   脉冲：0.30 s（横移排查中尝试 0.60 s）

### 4.1 后退

命令实际发送：

``` text
MOVE {'x': -0.3, 'y': 0.0, 'z': 0.0}
```

B2 返回 MOVE 响应后自动发送 STOPMOVE。

结果：

-   后退 3 次；
-   实际方向正确；
-   3 次均产生明确位移；
-   3 次均自动 StopMove。

**结论：后退 3/3 PASS。**

### 4.2 左横移

程序中 `a` 键实际发送纯横向：

``` text
y = +lateral_speed
```

不存在代码层面的 x/y 混合。

依次测试：

  lateral_speed      pulse 现象
  --------------- -------- ----------------------------------
  0.08 m/s          0.30 s 有向左后动作趋势，无明确平移
  0.08 m/s          0.60 s 有动作趋势，无明确位移
  0.10 m/s          0.60 s 仍只有趋势
  0.15 m/s          0.60 s 动作幅度增大，但仍无明显横向位移

项目安全程序的横向上限为 0.15
m/s，因此没有为了"测出来"而擅自突破安全限制。

**结论：左横移 FAIL / 未验收。**

控制命令和自动停车链路有效，但没有找到能够产生明确横向平移的已验证安全参数。

### 4.3 右横移

由于左横移在允许范围内没有找到有效参数，没有继续盲目强测右横移。

**结论：Pending / 未完成。**

### 运动测试补充

此前前进测试已发现：0.10--0.20 m/s 主要表现为腿部动作，0.30 m/s

## 9. RTAB-Map 第一次实机启动：QoS 问题

第一次启动 RTAB-Map：

-   `frame_id = base_link`
-   `odom_frame_id = odom`
-   `map_frame_id = map`
-   `subscribe_scan_cloud = true`
-   成功进入 SLAM mode
-   成功订阅 topic 名称 `/b2_slam_3d/cloud_sync`

但出现：

``` text
New publisher discovered on topic '/b2_slam_3d/cloud_sync',
offering incompatible QoS.
Last incompatible policy: RELIABILITY_QOS_POLICY
```

随后每 5 秒：

``` text
Did not receive data since 5 seconds!
```

### 根因

RTAB-Map 安装包明确说明：

``` text
qos_scan:
0 = system default
1 = Reliable
2 = Best Effort
```

而 `sensor_time_sync` 的 cloud publisher 使用 sensor-data QoS（Best
Effort）。

原配置：

``` yaml
qos_scan: 0
```

与 cloud publisher 实际 QoS 不兼容。

### 修复

在：

``` text
src/b2_slam_3d/config/rtabmap_3d.yaml
```

加入：

``` yaml
subscribe_scan: false
subscribe_scan_cloud: true
qos_scan: 2
```

这是今天必须保留的关键修改。

## 13. B2 横向运动最终实机验证

### 13.1 初始现象

最初 `safe_motion_test.py` 的横向速度上限为
`0.15 m/s`，每按一次运动键只发送一次 `MOVE`，随后由 watchdog
在设定时间到达后发送 `STOPMOVE`。

今天依次测试左横移：

``` text
vy = +0.08 m/s
vy = +0.10 m/s
vy = +0.15 m/s
```

其中 `0.15 m/s` 还分别测试了约 `0.60 s` 和 `1.00 s`。

现象一致：

-   B2 有向左运动/跨步趋势；
-   随着 `vy` 增大，动作幅度增大；
-   但机身没有形成肉眼可确认的实际横向位移。

因此原先 `0.15 m/s` 的程序测试上限不足以验证 B2 的有效横移。

### 13.2 持续刷新 MOVE 对照实验

检查 Unitree B2 官方 Sport Client 示例后发现，官方示例主循环约为 50
Hz，并在循环中调用 `Move()`。

为排查"单次 MOVE 是否导致横移无法建立"，临时将 `safe_motion_test.py`
改为：

-   按一次 `a/d` 后保存当前 MOVE；
-   timer 每 `0.05 s` 重发一次，即约 20 Hz；
-   到达 `motion_pulse_sec` 后仍强制发送 `STOPMOVE`；
-   不改变 `x/y/z` 命令含义。

随后逐级测试：

``` text
|vy| = 0.15 m/s -> 无明确位移
|vy| = 0.20 m/s -> 无明确位移，动作幅度增加
|vy| = 0.25 m/s -> 无明确位移
|vy| = 0.30 m/s -> 出现明显实际横向位移
```

`0.30 m/s` 时：

``` text
MOVE api_id = 1008
STOPMOVE api_id = 1003
```

均得到正常响应，自动停车正常。

### 13.3 单次 MOVE A/B 对照

为了判断成功是否由 20 Hz 重复发送导致，又将 `safe_motion_test.py`
恢复为原始设计：

``` text
按一次 a/d
    -> 只发送一次 MOVE
    -> 等待 motion_pulse_sec
    -> 自动发送 STOPMOVE
```

保留横向速度 `|vy| = 0.30 m/s`，再次进行横移。

结果：

-   单次 `MOVE` 同样产生明确横向实际位移；
-   `api_id=1008` 响应正常；
-   约 1 s 后 `STOPMOVE api_id=1003` 正常；
-   自动停车正常。

因此本次 A/B 实验表明：

> 在今天的 B2 实机条件下，约 20 Hz 重复发送 MOVE
> **不是实现横移的必要条件**。决定是否出现明显横向位移的主要实验变量是横向速度；`|vy|=0.30 m/s`
> 可以产生明确位移，而 `0.08–0.25 m/s` 未产生明确位移。

这里的 `0.30 m/s` 是**今天这台
B2、当前场地、当前运动模式下的实机测试结果**，不应扩大表述为所有 B2
的官方最小横移速度。

### 13.4 左右横移重复性

在有效参数下：

``` text
lateral_speed = 0.30 m/s
motion_pulse_sec = 1.00 s
```

完成：

-   左横移：3/3 成功；
-   右横移：3/3 成功；
-   每次均产生明确实际横向位移；
-   每次均能自动 `STOPMOVE`。

随后又用恢复后的"单次 MOVE"方式进行了 A/B 对照，同样成功产生横向位移。

**H2 左右横移最终结论：PASS。**

### 13.5 `api_id=1034`

横移测试期间多次观察到：

``` text
api_id=1034
data=
```

其中部分情况下约每秒出现一次。

今天没有在已检查的 B2 Sport API 定义中确认 `1034` 的准确含义，因此：

-   记录该现象；
-   不将其解释为错误码；
-   不根据该 ID 推断机器人状态；
